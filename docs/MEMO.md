## 2026-09-29: Phase 1 Adapter 実装時の観察

### 背景
C / Python / TypeScript の Mapping を作成した際に気づいた、言語間の差異と既知の制約。

### 内容 / 観察結果
- ~~文字列リテラルは部分木ごと 1 トークンにしている。そのため f-string / template string 内の埋め込み式はトークンにならない。~~ → Phase 1 レビューで、埋め込み式が IR ノードごと消えて Complexity 等も過小評価されると判明。`interpolations` で解消（ADR-0004 改訂）。
- Python のメソッドの `self` / `cls` は引数として数える。Java 等の暗黙の `this` とは数え方が異なる（Parameter Count は Partially Language Dependent）。
- Python `match` の `case _:` はワイルドカードだが `case` として数える（C の `default` と異なり、構文上は通常の case と区別されないため）。
- Python の docstring は `expression_statement` なので Statement として数えられる。
- C の `for (int i = 0; ...)` の初期化子は `declaration` として Statement に数えられる。Python の `for` には相当する宣言がない。

- Java の `case 1: case 2: 文` は 1 つの `switch_block_statement_group` になるため、case は 1 つと数える（C では 2 つ）。

### 気になる点 / TODO
- Documentation（Phase 3）で、Python docstring をドキュメントとして扱う方法を決める必要がある。

## 2026-09-29: Phase 2 実データでの負荷試験（Python 3.14 標準ライブラリ + site-packages）

### 背景
大規模コードベース（PLAN §13.3）での挙動を、実在のコードで確認した。

### 内容 / 観察結果
- 対象：2,469 ファイル、約 104 万行（release ビルド、単一スレッド）
- 実行時間：6.5 秒。**ピークメモリ 2.7 GB**
  - 全ファイルの IR（ソース全文・ノード・トークン）をメモリに保持したまま計算しているため。プロジェクト単位の重複検出・Halstead の異なり数が全ファイルを必要とする
- Python は全ファイル解析成功。失敗 43 件はすべて C / ヘッダファイル
  - 原因：`#ifdef __cplusplus` / `extern "C" {` / `#endif` のように、プリプロセッサ条件をまたいで波括弧が対応しない書き方。tree-sitter-c はこれを ERROR にする
  - C ヘッダではごく一般的な書き方なので、現状（ADR-0005：ERROR を含む木は解析しない）では C ヘッダの多くが解析できない
- プロジェクトの重複率 49%：大半は `idna/uts46data.py` や `pwnlib/constants/*` などの生成データ表。正規化トークン（ADR-0009）では正しく Type-2 クローンと判定される（ADR-0009 の制約どおり）

### 気になる点 / TODO
- **要判断**：C のプリプロセッサ条件による解析失敗をどう扱うか。選択肢
  1. 現状維持（失敗として明示）
  2. ERROR ノードを含む木でも、ERROR 部分を除いて解析を続ける（ADR-0005 の変更が必要。値の妥当性が下がる）
  3. `#if` 系の片側の分岐だけを残す簡易前処理を Adapter に入れる（C / C++ 固有処理）
- メモリ：IR からソース全文とトークン文字列を持たない構造にする、または重複検出用の正規化トークン列だけを残して IR を捨てる、などで削減できる。PLAN §13.3 は目標値を後から決めるので、今は測定値の記録にとどめる
- 生成コード（データ表）の除外オプションは、スコープ外として見送り

## 2026-09-29: Phase 3 言語追加時の観察

### 内容 / 観察結果
- `.h` は C として解析する。C++ のクラス等を含むヘッダは解析エラーになる（拡張子から言語を推測しない方針：ADR-0005）
- Rust の `match` の `_ =>` は Python の `case _:` と同様に case として数える
- Rust のマクロ呼び出し（`println!(...)` 等）は Call として数えるが、引数は token_tree で構文解析されないため、中のコードは IR に現れない
- Rust の `?` 演算子（早期 return）は判定点にしていない
- Go には三項演算子がないため、等価テストのフィクスチャでは同じ判定数になる `if` 文で書いた
- C++ の Mapping は C の表を含む形で別に書いた（表の結合の仕組みを入れるより、言語ごとの宣言的な表として読める方を優先）

### 気になる点 / TODO
- `.h` を C / C++ のどちらとして扱うかを利用者が指定できる仕組みは、必要になったら検討する
