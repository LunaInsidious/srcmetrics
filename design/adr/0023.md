# ADR-0023: 利用者向けドキュメントを VitePress で GitHub Pages に公開し、開発者向け文書と分ける

- **Status:** Accepted
- **Date:** 2026-09-29
- **Deciders:** lunaInsidious, Claude
- **Tags:** docs, release

## Context

### Problem

ライブラリ・CLI の利用者向けに、読みやすいドキュメントサイトを GitHub Pages に置きたい。一方、要求仕様・技術仕様・ADR・MEMO は開発のための文書で、利用者が読むものではない。

## Decision

- **利用者向け**：`docs/` を VitePress のルートとし、GitHub Pages に公開する。英語（`/`）と日本語（`/ja/`）
  - ガイド（導入、CLI、出力形式、ライブラリ、HTTP API、実験的モデル、対応言語と制約）
  - メトリクス定義（`docs/metrics/`。コードの定義から生成し、`tests/docs.rs` で同期を検査。定義文は英語のみ）
  - サイトを正とし、ページ構成は VitePress の前提で設計する（1 ページ 1 目的）
- **開発者向け**：`design/`（SPEC.md、adr/、MEMO.md）。サイトには載せず、GitHub 上で Markdown として読む。VitePress 専用の記法は使わない
- README.md / README_ja.md は GitHub と crates.io のトップページとして残し、概要とサイトへのリンクに絞る（ガイドの内容を重複させない）
- `package.json` はリポジトリ直下に置く（VitePress の標準構成）。Rust のビルドとテストは Node を必要としない
- GitHub Actions で main への push 時にビルドし（リンク切れで失敗させる）、GitHub Pages にデプロイする

### Rationale

- OSS の利用者向けドキュメントと、設計の経緯を記録する文書は読み手が違う。混ぜると利用者にとって読みにくい
- モノレポなので、原本をサイト側に置いても修正の手間は変わらない。既存の Markdown の形にサイトを合わせる必要はない

## Alternatives Considered

### 既存の Markdown（README、PLAN、docs/*）をそのまま原本として参照するサイト
**Cons** ADR 23 件が 1 ページ、ガイドが README 1 枚になるなど、既存の文書の形にサイトの構成が縛られて読みにくい。開発者向け文書も利用者の目に入る
**Rejected because:** 一度この形で作り、読みにくいと判断した

### mdBook
**Rejected because:** 多言語サイトの標準的な仕組みがない。利用者の指定が VitePress
